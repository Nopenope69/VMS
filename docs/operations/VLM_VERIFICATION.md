# Alarm second opinion (Phase 5 Wave C, ADR 0005)

Status: **built, and shown to work with the real model on public-domain pictures. Off by default, and the
model is not approved to run in the product yet** (it is a candidate model; see "Turning it on"). How well it
judges real CCTV alarms has not been measured.

## What it does

When an alarm is raised by an AI detection, a small vision-language model running on the appliance looks at
the detection's picture and answers one question: "Is there a *person* (or *car*, *truck* ...) in this image?"
The answer is **yes**, **no** or **unclear**, with a short reason. Operators see it in the resolve dialog as
"AI second opinion (advisory)".

It is **advisory only**. It never acknowledges, resolves, silences or downgrades an alarm, and never changes
what is notified. The worker writes only its own `VlmVerification` rows. A model that says "no" to a real
intruder must not be able to hide one; that is why it cannot act.

## How it is built

* **Model:** SmolVLM2 2.2B Instruct (Apache-2.0 weights), GGUF Q4_K_M plus its Q8_0 vision projector, pinned by
  SHA-256 in `scripts/models/models.lock.json` (the hashes match the Hugging Face LFS records).
* **Runtime:** llama.cpp's `llama-server` (MIT), built from tag `b11277`, commit
  `eae11d2217fe9225d1aaba48773b6cca45ae4de9` (`services/ai-worker/Dockerfile.vlm`; the build fails if the tag
  moves). The ai-worker (`AI_WORKER_MODE=vlm`, port 7014) starts llama-server itself as a child process, on
  loopback, with a fresh random API key and the model files it has just verified; it then checks that the
  server reports the pinned build and the verified model path. So the model that answers is the one named in
  provenance.
* **Prompt:** a fixed, versioned template in `scripts/models/pipelines/vlm-smolvlm2-v1.json`. Callers only name
  an object class from the pipeline's list; no free text crosses the contract. Greedy decoding
  (temperature 0), fixed seed, output constrained by a JSON schema to `{answer, reason}`; anything else is an
  error, never a guessed answer. The SHA-256 of that pipeline file is the model identity stored with each
  answer, so a change to the template or settings is a new model.
* **Which picture:** the alarm's triggering detection (found through the inference id its canonical event
  recorded; no link, no question), its snapshot frame if still on disk under an allowed root, else its stored
  object crop checked against the crop's SHA-256. The SHA-256 of what was sent is stored with the answer. No
  copy of the image is kept.
* **When:** every `VLM_VERIFY_INTERVAL_MS` (default 15 s) for alarms newer than `VLM_MAX_ALARM_AGE_MS`
  (default 1 h), newest first, one at a time.
* **Contract:** `ai-adapter.v1.1` task `vlm_verification`: `vlmQuery: { targetClass }` in,
  `verification: { targetClass, answer, reason, promptSha256 }` out. The backend client checks health, the
  descriptor, the model registry and the provenance of every answer.

## API

* `GET /api/v1/alarms/:id/second-opinion` (camera viewers): the stored answer(s), marked advisory.
* `GET /api/v1/alarms/second-opinion/agreement?from=&to=&modelSha256=` (alarm-feedback permission): how the
  answers compare with operator verdicts (true/false alarm) for alarms that have both. It reports the share of
  operator-marked false alarms the model answered "no" to, the share of "no" answers that were false alarms,
  and the share of **true** alarms the model doubted (the harmful error), each with a 95% Wilson interval. It
  says `EVALUATED` only with at least 100 such alarms (a proposal, not a standard).

## Turning it on

1. Fetch the files (about 1.7 GB, SHA-256 verified):
   `scripts/models/fetch-model.sh smolvlm2-2.2b-instruct-q4km` and
   `scripts/models/fetch-model.sh smolvlm2-2.2b-instruct-mmproj-q8`.
2. **A human approval is required.** The weights are Apache-2.0, but the training mix has mixed or unclear
   licences (some instruction data generated by other models, video sources). Until
   `scripts/models/model-license-exceptions.json` approves both SHA-256s, the worker refuses
   (`LICENSE_REJECTED`, health FAILED) and nothing is asked.
3. `docker compose --profile vlm up -d vlm-worker`. It builds llama.cpp from source the first time.
4. Set `VIGILONE_FEATURE_VLM_VERIFICATION=true` and `VLM_ADAPTER_URL=http://127.0.0.1:7014` on the backend.

## Measured, and not measured

Measured on the build machine (4 cores, `VLM_THREADS=4`):

* Eight yes/no questions on four public-domain pictures (person, cat, coffee cup, camera): 8/8 correct, the
  same answer and reason when asked again (`services/ai-worker/src/__tests__/goldenVlm.test.ts`). The smaller
  SmolVLM2 500M was tried first and got 5/8, answering "yes" while its own reason said "no"; it was rejected.
* About 11 to 16 s for the first question about a new picture, about 2.5 s for another question about the
  same picture. Each alarm is a new picture, so expect the longer figure, and longer with fewer threads.
* llama-server peaked at about 3.0 GB RSS; the compose limit is 4 GB.

Not measured:

* **Agreement with operators on real alarms** (the Phase 5 exit gate for this feature). It needs a pilot site
  whose operators record true/false verdicts; the agreement endpoint then reports it.
* Night-time, infrared, low-resolution and crowded scenes, which are where it matters and where small VLMs
  are known to be weak.
* Speed on the reference appliance.
